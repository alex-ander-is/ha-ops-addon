# UI Component Audit and Replacement Plan

Status: proposed for user approval. This document delivers an audit and a scoped replacement plan. Frontend implementation requires a subsequent approval naming the phases and options to implement.

## Scope and evidence

The audit covers all six Lit components and render helpers in [frontend source](ha-ops/frontend/src/ha-ops.js), the [global stylesheet](ha-ops/app/static/ha-ops.css), the [static shell](ha-ops/app/static/index.html), the committed [generated bundle](ha-ops/app/static/ha-ops.js), [render_page](ha-ops/app/web.py#L387), the [Vaadin migration plan](ha-ops/docs/vaadin-ui-migration-plan.md), and the [service-branch merge contract](ha-ops/docs/service-branch-merge-contract.md). Future edits belong in source; rebuild the committed bundle after an approved source change. The server serves the same inert shell; HTTP fallback is command transport through this client. There is no separate server-rendered control contour to replace.

This is a source and installed-SDK audit, not a claim of live rendered verification. Compatibility preflight found no open central compatibility-plan items and reused the existing version snapshot. No live query or release-note research was needed for the proposal.

The [manifest](ha-ops/frontend/package.json) and [lockfile](ha-ops/frontend/package-lock.json) pin eight direct Vaadin packages at **25.2.8**: Badge, Button, Checkbox, ConfirmDialog, Details, ProgressBar, Select, and TextField. Their installed manifests match and declare Apache-2.0. Dialog, Item, and ListBox are transitive **25.2.9** packages; a future direct import must become a declared direct dependency. The whole dependency tree is not uniformly 25.2.8.

Grid, RadioGroup, Tooltip, AppLayout, HorizontalLayout, VerticalLayout, FormLayout, Aura, and Lumo packages are absent from the audited lockfile and installed tree. Their selected package APIs, feature availability, and licensing have not been verified by this offline audit. Phase 4 makes their evaluation conditional; no dependency installation or Commercial Feature is approved.

## Theme correction and contrast

Two preexisting normal-text contrast defects follow directly from source and the explicit local dark fixture in [backup-continuation.mjs](ha-ops/tests/browser/backup-continuation.mjs#L201):

| Text / source | Foreground / fixture surface | Calculated ratio | Required acceptance |
| --- | --- | --- | --- |
| Apply backup warning, source line 664 | `#92400e` / `#1d232a` | **2.23:1** | At least **4.5:1** on actual composited background |
| Review flag, source line 470 | `#82071e` / `#1d232a` | **1.51:1** | At least **4.5:1** on actual composited background |

Ratios use WCAG relative sRGB luminance and `(lighter + 0.05) / (darker + 0.05)`. They describe the source colors on this harness surface, not a measured live HA theme. Existing [badge dark/forced-color assertions](ha-ops/tests/browser/backup-continuation.mjs#L201) test badges, not warning-message text contrast. Add message and Review assertions after approval.

Create one inherited bridge from HA `--ha-*` inputs to verified base tokens: surface to `--vaadin-background-color`, primary text to `--vaadin-text-color`, muted text to `--vaadin-text-color-secondary`, tested borders to `--vaadin-border-color`/secondary, and visible focus to `--vaadin-focus-ring-color`. Map spacing/radius where geometry permits. A primary button still needs its explicit `--vaadin-button-*` palette; secondary/warning also need retained app semantics. Current `--lumo-*` assignments do not establish a loaded Lumo theme.

Complete the app-specific `--ha-ops-*` bridge for border, code surface/text, muted text, and paired add/delete/hunk foreground/background. Introduce tested semantic notice/Review text tokens rather than assuming the existing warning accent is readable text. Audit the fallback header `#f6f8fa` and border `#d0d7de` too. Inherited tokens must work in light DOM, shadow roots, both dialogs and any approved Select popover after an HA theme change while mounted. Preserve forced-color system-color/focus rules. Keep explicit disabled styling, including native dialog buttons; SDK opacity 0.5 alone fails the repository appearance requirement.

## Four phases after approval

1. **P0/P1: contrast, token bridge and proven retirement.** Correct both contrast defects first; establish the shared bridge and disabled styles; review fallback/code/table palettes; remove only proven inactive/unreachable CSS. Acceptance: normal warning and Review text reaches 4.5:1 in explicit HA light/dark fixtures; focus and forced-color borders remain visible; backup action order/wording and badge semantics remain intact; no content disappears; no new dependency.
2. **P1: native dialog API and shared app compositions.** Use native version-dialog reject API, shared Details surface/overflow rules, one persistent notice composition, and the existing shared Badge. Preserve native behavior, all safety fences, lazy loading and stable rendered rows. Decide Review badge semantics before any badge substitution. Diff style consolidation must preserve both renderers and can be deferred.
3. **P2: optional preview Select.** Replace only the preview-local HA/Git button pair if the added menu interaction is approved. Preserve every choice/default/reset/transport invariant below. Recovery action Buttons remain their own immediate-command flow. Retaining the current preview buttons is a complete valid outcome for this phase.
4. **P3: separate evidence and design decisions.** Evaluate Grid for tables/fallback, RadioGroup for visible choices, Tooltip for Unicode, or the installed indeterminate ProgressBar only for a demonstrated user benefit. Grid/RadioGroup/Tooltip need exact pinned 25.2.8 source/API, package and feature license checks, direct-dependency declaration, bundle-cost comparison, and a keyboard/phone/long-data prototype before installation or selection. Show the new layout before approval. A Lumo/Aura/theme or layout-package migration is a separate scope decision.

### Select behavior contract

Use explicit nonempty item values `ha` and `git`, existing direction-aware labels, an accessible chooser label and an unresolved placeholder. Selected Save conflicts start empty; selected Apply conflicts visibly default Git. Preserve non-conflict defaults (Save HA, Apply Git), unselected-side retention, running/unselected disabled state, and a separate Wrap Lines control. Listen to user `change` for one local update; never derive command dispatch from value-changed.

Initialization, programmatic state patches, mouse/keyboard selection and wrapping send **zero commands**. Only final Confirm submits one complete selected-path/choice batch. Selected Save conflicts with an empty choice block Confirm. Enter/Space/Escape/arrows and pointer interaction inside the Details summary must not accidentally toggle expansion or lose focus. The menu tradeoff needs user approval; RadioGroup is an alternative only after the separate SDK/license/dependency evaluation.

### ConfirmDialog behavior contract

The version dialog currently acknowledges through the custom reject button click and through cancel/Escape. SDK setup adds a reject listener to the slot too. Replace the slot/click combination with rejectText/rejectTheme and **one** reject acknowledgement handler; retain the cancel/Escape acknowledgement contract. Reload remains confirm. Outside clicks remain prevented; preserve focus trap/restoration and initial confirm focus. Do not route both click and reject to acknowledgement.

The general mutation dialog keeps cancel as clearing its pending command; it must not acquire version-dialog acknowledgement behavior. Test mouse/Enter/Space on every button, Escape, outside click, focus restoration and one execution per intended action. Use documented min/max-width tokens or supported dialog properties; the inactive `--vaadin-confirm-dialog-width` declaration does not prove a supported token. Changing Escape to a dismissal without acknowledgement, initial focus, labels, or action order requires a separate behavior decision.

HaOpsApp static styles (including version-dialog and duplicate deleted-device declarations) are inactive under its root override. Remove them without changing createRenderRoot or reviving their visual design. Live deleted-device styles remain in the global stylesheet.

### Refresh, restart and version lifetime

Add no persistence for chooser/notice authorization. Reload/new tab starts an empty local draft; content/cursor/generation/backend-version changes reset selections, choices, submitted/refusal state, wrap draft and Save subject identity. Same-content updates and decision revision changes retain the current draft, mounted expanded DOM and focus. Late lazy responses cannot restore stale content. Backend startup/version repair clears warning authority; consumed acknowledgement never returns through recovery or a UI rollback. Existing sessionStorage log-scroll behavior remains independent of authorization. Any new widget persistence requires explicit refresh/restart/version reset rules and regressions.

## Risks and rollback

The principal failure modes are lost semantic colors from unsupported theme variants, incomplete shadow/overlay token inheritance, stale or auto-selected choices, duplicated dialog events, deleted active CSS, hidden long content, lost recovery roles/fences, and unchecked dependencies/licensing. The acceptance matrix gives proof for each class. Keep the disproved overlay-reparenting concern separate from the valid need to check actual inherited overlay colors.

Deliver approved phases as reviewable source/bundle changes. If visual or interaction acceptance fails, revert the affected phase together with its generated bundle and dependency/lockfile changes, then repeat affected local checks. Restore the last verified native preview buttons if Select fails its contract. A code rollback cannot undo live operations or restore expired authorization; do not modify backend state to make old UI decisions reappear. This documentation task itself requires no application rollback.

## Decisions for user approval

- Approve implementation of **phases 1–2**, or select a narrower phase. These use the installed components and preserve the current workflow; contrast fixes are highest priority.
- For **Review**, keep emphasized text with a readable semantic token (recommended default), or approve a Badge and its intended neutral/warning/error meaning. Phase 1 contrast does not depend on a Badge decision.
- Separately approve **phase 3 Select**, accepting its extra menu interaction, or keep the visible HA/Git buttons.
- Separately select any **phase 4 research/prototype**. Dependency installation, selected feature licensing, and a new table/fallback layout require approval after evidence. ProgressBar can use the existing dependency but still needs acceptance of the added presentation.

Approval of the audit or document is not frontend implementation approval. Approval of selected implementation phases does not authorize dependency installation outside that scope, publication, or live-system actions. This task changes only repository-root UI_COMPONENT_AUDIT.md. It needs no App version/changelog/tag change and does not change product code, TESTING, or user TODO wording/status. Its documentation verification consists of exact source/SDK/reference checks, Markdown/diff checks and three independent audit passes before a separate documentation commit.
